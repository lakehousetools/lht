# Tests

## Current coverage

| Suite | Location | Requires | Runs by default? |
|---|---|---|---|
| Unit | `tests/unit/` | Nothing -- no network, no credentials | Yes -- plain `pytest` |
| Integration: full sync lifecycle | `tests/integration/` | A configured Salesforce + Snowflake connection, network access | No -- `pytest -m integration` only |

**Run with the `pytest` console script, not `python -m pytest`, from the repo
root.** `python -m pytest` prepends the current directory to `sys.path`, and
the dev-convenience `lht.py` at the repo root then shadows the real `lht`
package (`src/lht/`), so imports resolve to the wrong module and tests fail
or behave inconsistently depending on collection order. `venv/bin/pytest` (or
just `pytest` inside an activated venv) doesn't have this problem. See
`ISSUES.md` ("`python -m pytest` imports the wrong `lht`").

## `tests/unit/` -- fast, no live credentials

Pure function / logic tests against `lht`'s internals, with Salesforce and
Snowflake faked out where needed (no real API calls, no real database, no
`~/.solomo/connections.toml` ever touched). Runs as part of a plain `pytest`
invocation.

- `test_field_types.py` -- Salesforce -> Snowflake/pandas type mapping
  (`util/field_types.py`), including that an unrecognized Salesforce field
  type raises `UnknownFieldTypeError` rather than killing the process, and
  that string fields are deliberately *not* length-bounded (a documented fix
  for numeric-looking strings like `"20"` round-tripping as `20.0`).
- `test_merge.py` -- `util/merge.py`'s `merge_into_target()`, with a fake
  Snowpark session that answers `DESCRIBE TABLE` from a canned column list
  and records every SQL statement executed. Regression-tests the two bugs
  fixed together on 2026-08-19: that a `MERGE` (not `INSERT`) is actually
  *executed*, that it has both a matched/UPDATE and not-matched/INSERT
  branch, and that no identifier in the generated SQL is quoted.
- `test_connections.py` -- `user/connections/manager.py`'s save/load/list/
  delete/primary-connection round-trip against `connections.toml`, with
  `get_solomo_dir()` monkeypatched to a pytest `tmp_path` for every test so
  nothing is ever read from or written to the real `~/.solomo` directory.

## `tests/integration/` -- full sync lifecycle

Drives the actual `lht` CLI (`lht sync`) against a live Salesforce org and
Snowflake database and checks the result at each stage, instead of testing
any single function in isolation. Ten tests, run in order, each depending on
state (created record ids, a pre-test baseline snapshot) left by the ones
before it:

1. **Baseline complete refresh** -- `lht sync --force-full-sync`; captures
   the starting row count and Id set to compare back to at the end.
2. **Create test records** -- creates N (default 10) Salesforce records from
   `<Sobject>.toml` (generated by `discover_fields.py` from real org
   metadata/data).
3. **Sync + verify create** -- runs `lht sync`, checks every created record
   landed in Snowflake with the right field values, and checks for duplicate
   rows (see below).
4. **Update test records** -- applies `[update_fields]` from
   `<Sobject>.toml` to all of them in Salesforce.
5. **Sync + verify update** -- re-syncs, checks the updated values landed,
   checks for duplicates again.
6. **Soft-delete test records** -- standard Salesforce delete (Recycle Bin).
7. **Sync + verify soft-delete marked** -- re-syncs, checks `ISDELETED =
   TRUE` in Snowflake.
8. **Verify soft delete in Salesforce** -- independent check directly
   against Salesforce (`queryAll`/`ALL ROWS`), not just via the sync result.
9. **Hard-delete test records** -- purges from the Recycle Bin
   (`DELETE /sobjects/RecycleBin`).
10. **Full sync + verify back to baseline** -- `lht sync --force-full-sync`
    again; checks the table matches the step-1 baseline (row count, no
    leftover test Ids) and has no duplicate Ids anywhere.

**Why the duplicate-Id checks matter:** a Salesforce `Id` is unique per
record, so the same Id appearing twice in the target table is always a bug.
Steps 3, 5, 7, and 10 each assert this, both for the test records specifically
and for the table as a whole. This is what caught (and will keep catching, as
a regression test) an earlier bug where `lht sync`'s incremental path
INSERTed every batch instead of merging, appending a duplicate row on every
re-sync of an already-loaded record -- now fixed via `merge.merge_into_target`.

**Why it's gated:** these tests authenticate for real, write to a real
Snowflake table, and create/update/delete real Salesforce records. They're
excluded from a plain `pytest` run (`addopts = "-m 'not integration'"` in
`pyproject.toml`) and only run when explicitly requested.

Setup, running instructions, and CLI flags: see
[`tests/integration/README.md`](integration/README.md).

Files:
- `test_sync_scenario.py` -- the 10 tests described above
- `conftest.py` -- fixtures (config, auth, Snowflake session, report) and the
  `--num-records`/`--keep-test-records` CLI options
- `lht_common.py` -- shared helpers (Salesforce REST calls, Snowflake
  verification queries, the step/report framework)
- `discover_fields.py` -- standalone script (not a test) that queries the org
  for valid Record Type Ids and realistic sample field values, writing
  `<Sobject>.toml`
- `cleanup_test_records.py` -- standalone script to hard-delete leftover test
  records from a failed or `--keep-test-records` run
- `config.toml` -- which org/database/sobject to run against (tracked in
  git); `<Sobject>.toml` is generated per-org and gitignored
